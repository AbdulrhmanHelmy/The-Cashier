# Product catalog

## Manual weight selling

Migration 084 adds `ProductDetails.SellingType` (`piece` by default, or `weight`). Existing product IDs, units, prices, stock, and invoices are untouched. The setting is independent of the Units directory and product-unit IDs. A new weight product retains its selected base product-unit relationship, but **one internal base quantity means one kilogram for that product**. No additional active unit conversions are allowed on a weight product. This prevents purchase and stock operations from giving an existing package conversion a new weight meaning. A saved product cannot switch selling type or base unit; create a new product instead of reinterpreting its existing stock/history.

For weight products the catalog shows `يباع بالوزن`, `سعر الكيلو`, and a reference purchase price per kilogram. The product detail presents its base quantity as `كجم` while the Units directory and stored unit definition remain unchanged. Staff enter purchase, count, adjustment, and transfer quantities in kilograms; Touch POS accepts grams or kilograms and stores kilograms at scale 6. No scale hardware, scale barcodes, or packaging conversions are implemented.

## Implemented scope

Phase 2 Tasks 2.1–2.2 provide a real SQLite-backed catalog for products, nested categories, units, configurable attributes/values, variants, SKUs, barcodes, and exact rational product-unit conversions. Products support name, optional description/category, base unit, `stock`/`service`/`non_stock` type, scale-4 non-negative sale price, nullable scale-4 non-negative reference purchase price, active state, archive state, migration-review state, timestamps, and optimistic `Version`. A default internal variant is created automatically for simple products; it remains hidden as an incomplete configuration until identifiers or variant settings are requested.

The Arabic RTL UI reuses the approved shell and components. The list supports server-side search, category/status filtering, bounded paging, edit, and administrator state/archive actions. Product Catalog is the primary visible entry; add, quick-add, and edit routes remain valid contextual/deep-link flows. Category and unit management are discoverable from the catalog and use full-width searchable tables with `+ إضافة تصنيف` / `+ إضافة وحدة قياس` actions. Create and edit use the shared compact centered modal form (inline validation, save loading state, guarded unsaved close, focus return, and no duplicate listeners); status can be activated/deactivated, while deletion is not exposed. Administrators can create a category beside the form selector without losing the mounted draft; successful creation refreshes the selector and chooses the new row. Product edit exposes capability assignment, attribute values, variant identifiers, barcode lookup, and exact unit conversion inputs; stock quantities and warehouse balances are deliberately not product-master fields and are read from the inventory ledger instead (see Task 2.4 below).

Product creation offers expiry tracking as its optional staff-facing switch. Expiry requires batches; IMEI requires serial tracking. Existing tracking assignments, conversions, identifiers and custom attributes are preserved during edits. Physical tracking identities and stock movements belong to inventory posting, never to the product save.

The compact RTL form retains its basic fields, barcode entry/generator, exact base-unit mapping and Save/Cancel footer. Failed requests retain the mounted draft. Changing the base unit of a saved product remains prohibited.

Sizes and colors are retired from UI, feature flags, activity recommendations, catalog contracts and barcode labels. Catalog rows contain variant counts and tracking badges, without retired value lists. Saved combinations show their existing name, SKU and barcode. Historical variant identities and database links are retained; they are never collapsed into a new simple variant. See [retired product attributes](retired-product-attributes.md) for API changes, the compatibility policy, legacy-edit restrictions and regression coverage.

## Money and legacy data

Migration 089 adds a nullable purchase price to each product unit. Additional units may store independent purchase and selling prices; a null purchase price retains the earlier product/variant reference-price fallback. Existing unit rows, conversions, invoices, and inventory values are unchanged by the migration. Purchase drafts choose a unit's configured purchase price when available and allow editing the posted price. Posted acquisition cost uses that invoice price and the exact base-unit conversion; stock remains one base-unit balance per warehouse, variant, and batch. A receipt in an additional unit updates that unit's selling price without overwriting the base unit's price.

Catalog sale price is stored in `ProductDetails.SellPriceScaled` as `long` at scale 4. Reference purchase cost is stored in nullable `ProductDetails.PurchasePriceScaled` using the same scale. `NULL` means unknown, especially for pre-hotfix products; it is never silently converted to verified zero and is not an inventory average cost. API values are strings such as `"12.3400"`. C# parses invariant decimals, performs checked multiplication by 10,000, rounds midpoint away from zero once, and rejects negative or overflowing values. Display precision remains a General Settings concern.

Migration 008 never drops or rebuilds `Products`. Valid legacy rows retain IDs, names, and original prices and receive details/default variants. Invalid legacy rows are retained, quarantined inactive with `review_required`, and recorded for administrator review; activation is blocked until a valid edit resolves the issue. `CatalogOperations` makes product creation retry-safe by operation key and request hash.

## Task 2.2 persistence and boundaries

Migration 010 adds product attributes, values, assignments, product units, variants, variant attribute combinations, SKUs, and barcode history. SKU and active barcode values are globally unique; variant combinations are unique per product; retired barcodes remain historical and cannot be used for lookup. Conversions use positive integer numerator/denominator pairs and are reduced/validated in the Application/Data boundary. Capability assignment is checked against effective feature state, while existing assignments remain readable when an administrator disables a capability. Barcode lookup is scanner-ready, authenticated, CSRF-free for reads, and still reports inactive/archived reasons without inventing inventory quantities.

## Deliberate limitations

Task 2.2 did not implement real warehouses, quantities, tracking identities/receipts, ledger movements, purchasing, or sales posting, and it added only product-level tracking configuration switches. Later phases now ship SQLite-backed warehouses, the immutable stock-movement ledger with its balance projection, batch/serial/IMEI identity records, persisted product reorder levels and unified alerts, and the operational `دليل المخازن` directory at route `warehouses-list`; the compatibility routes `warehouse-add`, `stock-adjustment`, `warehouse-transfer`, and `stock-movements` redirect to that directory, which reads real warehouse rows rather than a mock dataset. FEFO lot auto-allocation and negative stock remain outside this catalog boundary. Durable FIFO costing of outbound stock exists only inside the inventory ledger; the catalog purchase price stays a reference value and is never substituted for an actual acquisition cost. A tracking switch alone still creates no tracking record or stock movement. Inventory balances are derived from the immutable ledger and must never be edited directly.
# Inventory integration in Task 2.4

Inventory attaches to the existing `ProductVariants.Id` and `ProductUnits.Id`. The catalog purchase price remains a reference, not recorded acquisition cost. Warehouse quantities and FIFO value are queried from `/api/inventory/balances` and are not editable product master fields. Tracking assignments remain enforced after posting history, including when global availability changes. The catalog row and compact badges remain unchanged; see [inventory-ledger.md](inventory-ledger.md).


Receipt purchase price is actual acquisition cost per selected unit and never uses the catalog reference fallback. Receipt selling price becomes the selected variant override in the existing pricing model, with product/variant version updates and catalog audit in the inventory transaction. For a product with exactly one variant, the base sale price and its legacy mirror also advance, keeping the ordinary catalog list consistent. Other variant overrides, multi-variant base prices and historical costs remain intact. Catalog detail and barcode lookup expose the effective variant price; product-level reference prices remain separate. See [inventory-fifo.md](inventory-fifo.md).

## Task 6: reorder point

Product Add, Quick Add and Edit share `حد إعادة الطلب`, default `0` (disabled). API `reorderPoint` is a nonnegative invariant decimal string with at most six fractional digits in the product's base unit. Migration 080 stores exact scale-6 `ReorderPointScaled`. Omitted create values become zero; omitted update values preserve the saved threshold for older clients. Product detail/list responses expose the field; optimistic versioning, aggregate updates and create replay identity include its meaning. Existing create hashes for disabled thresholds remain compatible. Threshold changes never move stock. See [unified alert semantics and tests](unified-alerts.md).
