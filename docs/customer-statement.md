# Customer statement and account operations

The Customers section exposes `customers-list` and `customer-statement` only. `customer-credit-payment` is a hidden compatibility redirect to the statement; its separate payment form is no longer an operational destination. Customer management stays unchanged.

The real statement reads `/api/customers` and `/api/customers/{id}/statement`. A persistent customer selector and date filters sit above debt and movement details. The screen shows current debt across all dates, opening balance for the selected period, period increases, collections/reductions and closing balance. Movements retain actual document references and saved notes. Filtering to older dates does not present an old period closing balance as the customer's current debt. There are no mock records or unavailable-invoice preview controls.

Clicking a row in `إدارة العملاء` passes that row's numeric customer ID as explicit workspace route state. The workspace remounts an already-open statement tab when new route state arrives, so switching rows never relies on a cached/default customer. Manual selector changes and date filters remain tab state. Each statement request captures both its customer ID and request generation; a response is rendered only while both still match, preventing slower responses for a previously selected customer from repainting the current statement.

The existing `/api/customers/{id}/transactions` endpoint powers two contextual dialogs: `increase` (إضافة مديونية) and `collection` (تحصيل من العميل). Inputs use positive decimal text with at most two decimals, local business-date defaults and saved notes. An increase may exceed the previous debt. Collection cannot exceed the current server-validated debt. Each dialog keeps one operation key, blocks repeated submissions, locks inputs during posting and uncertain retries, and resubmits the exact original command after a lost response. Definitive validation failures retain editable inputs. Success reloads the statement without remounting selectors/date filters; a movement outside the selected dates is explained in the success notification.

Application validation and the existing SQLite writer transaction remain the financial boundary. Transaction entry, idempotency identity and customer balance projection commit together or roll back. The projection checks overflow before inserting an increase. Current debt comes from the exact ledger aggregate; no historical entries are changed. A new manual statement collection also requires payment method and an explicitly selected compatible active treasury account, deposits once, and links the movement to the collection ledger entry in the same transaction. It does not allocate payment to sales invoices. Sales invoice-specific payment/refund workflows retain their own transaction boundaries.

The old frontend statement referenced `context` without receiving it, causing loading to fail. Renderer dispatch now supplies the real render context and request-generation/active-route guards prevent late responses repainting another customer/page. The old all-time SQL reader initialized its running balance with the sum of every movement, then added every movement again. It now starts an unfiltered statement at zero; a date-filtered statement starts with entries strictly before `from`. `currentBalance` is independently derived from the same full ledger rows, and `notes` is exposed on movements. The schema is unchanged and no migration is required.

Persisted installment sales add an installment-sale debit for the total contract, a down-payment collection when present, and each installment settlement as an individual customer-ledger collection. The statement descriptions identify these movements and current/closing balances include them. Contract/schedule/payment rows and ledger entries share one SQLite transaction; see [installments.md](installments.md).

The statement GET and transaction POST require an authenticated session and effective `customer-statement` screen access for cashiers; POST also requires CSRF. Administrators retain access. Stored old-route permissions are not silently expanded to the new combined workflow. Historical operation-key ownership/conflict behavior is unchanged. Numeric overflow returns an Arabic validation envelope; logged SQLite failures return 503 and the client keeps retry identity.

## Verification

`CustomerStatementTests` covers all-time versus filtered balances without double counting, independent current balance, notes, persisted restart reads, replay, overcollection, injected late-balance failure rollback/retry, increase beyond previous debt and overflow rejected before any ledger insert. `CustomerStatementApiTests` exercises actual cookie/CSRF/screen permissions, exact decimal-text requests, increase/collection/replay, rejected overcollection, current/closing balance and persisted reads.

The executable `frontend/tests/customer-statement-tests.js` covers runtime context wiring, explicit selected-customer initialization, existing-tab reopening, rapid customer switching, live API loading, debt/notes rendering, both transaction types, exact payloads, duplicate and lost-response guards, preserved fields after rejection, precision validation, disabled zero-debt collection, mounted filters/customer selector, date validation, retry/stale results and the two-entry sidebar plus hidden old route. The registry suite also executes the customer-row click and verifies that its exact persisted ID is passed as route state.

On 2026-10-28, `dotnet test AlKhayal.slnx --no-restore -m:1` passed all 179 integration and 50 unit tests. `node --check frontend/js/modules/renderers.js` and the complete `node frontend/tests/run-tests.js` suite passed (101 registered routes). The UI and its dependencies built successfully with zero warnings/errors in the separate output directory using `dotnet build src/AlKhayal.UI/AlKhayal.UI.csproj --no-restore -m:1 -p:OutDir=D:/k/AlKhayal/.tmp/customer-statement-validation/`; this avoids replacing DLLs held by the operator's running desktop. Restart through the normal `dotnet run --project src/AlKhayal.UI` after closing the current app to copy updated binaries. NuGet vulnerability metadata was unavailable (`NU1900`). Tests use disposable databases, never mutate the operator database, and do not establish native visual/DPI or Windows 7/Chromium 109 qualification. No dependency or runtime target changed.
