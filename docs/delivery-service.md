# Delivery service

The application entry point must include `delivery-orders` and `drivers-management` in its implemented-route dispatch list. Both routes use `frontend/js/modules/delivery.js`; the definitions in `renderers.js` are loading placeholders. Driver management loads real API records, retains inactive drivers for editing, shows an explicit empty/retry state, and pages its search results in the browser (25 rows per page). The delivery order list uses server-side pagination and includes inactive historical drivers in its filter. The Touch POS picker requests active drivers only for new assignments.

Migration 083 adds `Drivers` and `SalesInvoiceDeliveries`. A delivery is an optional sale snapshot: it records the chosen active driver, delivery contact/address, fee and lifecycle status without changing FIFO product cost or treating delivery completion as a collection.

Customer profiles use the existing `Customers.Phone` (primary phone) and `Customers.Address` columns from migration 004, plus nullable `Customers.SecondaryPhone` from migration 083. Customer Add/Edit exposes all three; the two optional values may be empty. Touch POS retains the selected search result's contact details even if later searches replace the result list. Opening delivery copies the selected customer's values into editable invoice-specific fields. Switching customers clears the prior delivery; reopening for the same customer keeps manual delivery edits. Posted delivery snapshots remain independent of later customer profile changes.

The delivery fee is added once to `SalesInvoices.TotalScaled` while draft creation/correction is in the same SQLite transaction. Cash, credit/customer balance, shift revenue, cancellation and correction therefore use the posted total unchanged. Drivers may be deactivated; old snapshots remain readable.

`GET/POST /api/delivery/drivers` manages الطيارين and requires the effective `drivers-management` screen grant for cashiers. `GET /api/delivery/orders` accepts `search`, `status`, `driverId`, `page`, and `pageSize`, returns `{ items, total, page, pageSize }`, and requires `delivery-orders`; it returns current posted delivery invoices only, excluding cancelled and superseded revisions. Its status endpoint accepts `pending`, `out_for_delivery`, `delivered`, or `failed`, requires the same grant plus CSRF, and rejects non-current invoices. Administrators retain access. `delivery` is an additional print document type and does not replace the ordinary sale receipt.

Delivery Orders opens the saved sales invoice by ID. If the operator switches workspace tabs during loading, the retained invoice view can finish rendering in the background. An open sale can edit delivery details through its existing draft or correction controls. The active-only picker displays an unavailable saved driver by name and asks the operator to choose an active driver or explicitly leave the order unassigned. The Driver Management editor keeps the dialog and input values available after a rejected save.
