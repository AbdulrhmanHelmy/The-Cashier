# Product reorder point and unified alerts

The product master owns a base-unit reorder threshold. Zero disables it. Active stock products produce exactly one live alert when `threshold > 0 && total <= threshold`: zero/negative total is `low-stock`, while a positive total at or below the threshold is `reorder`. Total includes every balance row linked through every product variant, with no warehouse, active-reference or batch exclusion. Inactive/archived product masters and service/non-stock products are excluded. A configured product with no stock history has total zero. Internal quantities use exact scale 6; API quantities remain strings.

The alert page is backed exclusively by the persisted SQLite projections for stock, remaining expiring batches, and unpaid customer-installment schedule rows. Expiry rows are identified by the stable batch and warehouse IDs, display the product, lot, warehouse, date, severity and that warehouse's exact positive remaining quantity, and disappear when that balance reaches zero. The same batch in two warehouses therefore produces two independently accurate rows instead of one merged quantity. Installment detail uses `scheduled - paid`; fully covered rows disappear. There is no demo/mock notification fallback; `other` is empty until a persisted supported event is implemented. Existing separate stock alert routes redirect to the unified page. Legacy stock-only permissions retain stock-only visibility and stock-only read actions; full Alerts grants retain all supported types. Related-record buttons open the exact product editor or customer installment contract when destination permission exists.

Badge semantics are **unread current alerts**: reading leaves the active row visible but reduces the badge. Read state is stored per authenticated user in `AlertReadStates` and survives application restarts. Both page and badge consume the same cached source, Mark All reloads the authoritative state, and a refresh failure is visible rather than presenting a known zero.

A single read returns all supported projections; it does not invoke valuation or query per row from the frontend. Successful product edits, stock posting/count/reversal, sale/purchase posting and return/correction operations, and installment creation/payment invalidate the shared snapshot. Draft saves, unrelated payments, category edits and unrelated writes do not query alerts. Coalescing and revision checks prevent redundant simultaneous reads and stale responses. Focus and an explicit refresh button capture external changes and date transitions without periodic polling. Other-terminal changes while the window remains continuously focused appear on the next relevant write, focus, or manual refresh; server push is outside this change.

Migrations 080 and 082 are additive. Migration 082 creates only the per-user read-state table and index and is transactionally verified against a disposable populated pre-082 fixture. No real database is opened or migrated during task verification. The desktop and licensing paths are unchanged. Runtime remains .NET Framework 4.8 / .NET Standard 2.0 and vanilla Chromium 109-compatible frontend code. Native Windows 7/WebView2/RTL visual verification remains deployment work.
