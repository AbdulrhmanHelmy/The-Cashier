# API contracts

`GET /api/settings/general` includes `showCashChangeCalculator`, defaulting to true. Administrators update it through the existing general settings PUT. Omitting it from a PUT preserves the stored value.

Header and Settings Global Search use bounded, same-origin reads. The [coverage table](global-search-coverage.md) lists the query fields, API routes and applicable grants. New directory search endpoints return record identities and display labels, with source-specific context used to open the selected record.

New posted sales persist actual and estimated cost parts. `GET /api/reports/net-profit` exposes `estimatedCogs`; product-profit summary and rows expose `estimatedCost`. These four-place decimal strings are null when cost evidence is incomplete. The net-profit value is operating profit for recorded sales and included expense vouchers, not business-wide profit. See [sale cost and profit scope](estimated-sale-profit.md).

## Cashier sale-price permission

`GET /api/auth/me/screen-access` includes `canEditSalePrices`. Administrators always receive `true`; cashiers default to `false` unless explicitly granted. Administrators manage it with `GET/PUT /api/users/{id}/sale-price-permission` and `{ canEditSalePrices }`. Sales draft creation/update, installment invoice creation, and posted-invoice corrections reject `manualPriceOverride: true` with HTTP 403 when the cashier lacks the grant. The permission covers manual selling-price changes in invoices and POS only; product-directory pricing remains governed by catalog permissions.

## POS stock visibility permission

`GET /api/auth/me/screen-access` includes `canViewPosStockQuantities`. Administrators always receive `true`; cashiers default to `false`. Administrators manage it with `GET/PUT /api/users/{id}/pos-stock-permission` and `{ canViewPosStockQuantities }`. For product-list requests with `posWarehouseId`, the Inventory API suppresses `availableQuantityScaled` for users without the grant. POS cards show `المتبقي: ...` only for authorized users. Other inventory endpoints and product-directory screens are unchanged.

## Return settlements

`GET /api/returns/invoice` includes `installmentContractId`, `contractNumber`, original invoice total, collected and outstanding amounts, the remaining schedule, and original payment instrument where applicable. `GET /api/returns/sales/{id}` includes `electronicRefundStatus` (`pending` or `confirmed`), original internal payment key, method, instrument, and confirmed external reference when applicable. `POST /api/returns/sales/{id}/confirm-electronic` requires the returns screen permission, session, and CSRF. Body: `{ operationKey, externalReference }`; it confirms only an existing pending electronic return, returns replay status for an identical retry, and rejects a different or duplicate confirmation. No provider call or treasury movement is implied.

## Atomic installment sales

`POST /api/sales/installments` requires session, CSRF and `installment-system` permission. Its body contains `{ invoice: { customerId, warehouseId, invoiceDate, paymentMode: "credit", immediateMethod: "credit", discount, lines: [{ variantId, productUnitId, quantity, unitPrice, discount, lotNumber?, expirationDate?, physicalUnits? }] }, downPayment, interestRate, interestReturnPolicy: "cancel"|"keep", installmentCount, intervalMonths, firstDueOn, treasuryAccountId?, operationKey }`. `interestRate` is a percentage with up to two decimals applied once to the amount financed after the down payment. Interest is stored on the immutable installment contract and added to the customer debt and schedule; it does not change the sales invoice total. `interestReturnPolicy` is fixed when creating the contract. It returns `{ contractId, contractNumber, invoice, replayed }` inside the standard envelope. The invoice and contract are posted in one SQLite transaction. `GET /api/customers/{id}/installments` includes nullable `salesInvoiceId` (null for legacy contracts), interest rate/amount and the return policy; sales invoice reads include nullable `installmentContractId`. `GET /api/sales/installments/{id}/invoice` permits the installment payment screen to read only a linked posted invoice. `POST /api/customers/{id}/installments` is closed with HTTP 410. Installment payment POST accepts optional two-decimal `amount`; omission pays the remaining scheduled amount. Schedule rows return `paidAmount` and `remainingAmount`. Collections are allocated to unpaid invoice principal first, then to contract interest, so invoice paid totals do not exceed invoice totals.

Sales return POST accepts optional `interestSettlement` (`cash` or `credit`, default `credit`). For contracts created with `interestReturnPolicy="cancel"`, a proportional share of the flat interest is canceled for returned goods. Unpaid interest reduces the contract schedule and customer debt; a paid share is refunded in cash or recorded as customer credit according to this field. The adjustment is append-only and committed with the return.

## Business data exports

`GET /api/exports/{dataset}/{format}` returns an attachment for an authenticated user with effective read access to the dataset screen. Formats are `xlsx` and `csv`; datasets are `products`, `customers`, `suppliers`, `warehouses`, `sales`, and `purchases`. Filters are explicit allowlists: products use `search`, `categoryId`, `isActive`; customers/suppliers use `search`, `status`; warehouses use `search`, `isActive`; invoices use `search`, `from`, `to`, `status`, `warehouseId`. Exports contain every matching row and accept no pagination parameters. CSV is UTF-8 with BOM and XLSX is an offline Open XML workbook. Errors use the standard envelope; success is raw attachment bytes.

Administrator-only business backup routes are under /api/settings/backups. GET returns configuration, recent status and history. PUT accepts { directory, enabled }. POST /create accepts an optional { directory } and returns the verified archive location. GET /download?name= serves a file from the configured directory as an attachment. POST /inspect streams an application/octet-stream archive and returns its manifest and a short-lived confirmation. POST /restore accepts { confirmation }, quiesces API activity, commits the replacement and returns the emergency archive location. All writes require the existing session CSRF header. Concurrent requests during restore receive HTTP 503. See [offline backup and restore](offline-backup.md).

## Product selling mode

Catalog product create/update accepts `sellingType: "piece" | "weight"`; omitted create values default to `piece`, and omitted update values retain the saved mode. Product list and detail responses include `sellingType`. A weight product must use its single base product-unit relationship; active additional conversions are rejected. Selling type and base unit cannot change after creation because that would reinterpret persisted stock. For weight products, `salePrice` and `purchasePrice` are per kilogram. Sales, purchase, inventory, and return quantity strings are kilograms with up to six fractional places; Touch POS converts manual gram input before sending these contracts. The API does not accept a separate gram unit or a scale device payload.

## Delivery service

`GET /api/delivery/drivers?search=&activeOnly=` lists طيارين. `POST /api/delivery/drivers` creates or updates `{ id, name, phone, isActive }`. Both require the effective `drivers-management` grant for a cashier. `GET /api/delivery/orders?search=&status=&driverId=&page=1&pageSize=25` returns `{ items, total, page, pageSize }` for current posted delivery invoices, excluding cancelled and superseded revisions; `POST /api/delivery/orders/{invoiceId}/status` accepts `{ status }` where status is `pending`, `out_for_delivery`, `delivered`, or `failed` and rejects invoices outside that current posted set. Both require `delivery-orders`. Administrators retain access; mutation calls also require the existing same-origin session and CSRF header.

## Unified alerts

`GET /api/alerts` returns the authenticated user's current persisted alerts with `id`, `type` (`low-stock`, `reorder`, `expiry`, `installment`, or supported `other`), title, detail, severity, optional date, and `read`. Stock alerts aggregate all warehouse and variant balances: zero stock is `low-stock`; positive stock at or below the configured reorder point is `reorder`, preventing duplicates. Expiry alerts include only positive remaining batches due within 30 days or already expired. Installment alerts include unpaid schedule rows due within 30 days or overdue. `POST /api/alerts/{id}/read` and `POST /api/alerts/read-all` persist read state and require the session, alert permission, and CSRF token.

Pre-Phase 9: product detail variants add `effectiveSalePriceExact`, an invariant scale-4 decimal **base-unit** string alongside the existing formatted price. Standard Sales/Touch POS convert that price by the selected unit's `numerator/denominator`, then round once to piastres; draft saves validate the same Application calculation. Existing barcode lookup price fields retain their base-unit meaning. Posting uses saved draft prices and tax facts. See [pricing/FIFO contracts and reporting limitations](phase-9/pre-phase-9-pricing-fifo.md).

Sales return posting may now make the sales-returns cashbox negative. For credit invoices it reduces current customer debt first (never below zero), then refunds the residual cash, including general-account collections. This changes existing return behavior without changing request contracts. Other withdrawal endpoints retain no-overdraft rules. See [sales-refund-overdraft.md](sales-refund-overdraft.md).

Purchase/sales invoice GET and list responses include `hasReturns`, `isFullyReturned` and `returnStatus` (`none` / `partial` / `full`), derived from persisted return quantities without changing `status`. See [returns-management.md](returns-management.md).

`/api/returns` exposes the unified persisted list/post contract, `/invoice` manual exact-number lookup, `/invoice/{type}/{id}` exact picker lookup, `/invoices` server-paged eligible invoice search, and `/{type}/{id}` saved-return detail. Picker parameters are `type`, `search`, `from`, `to`, `status`, `page`, and bounded `pageSize` (5–50). Session and effective `returns-overview` permission apply to every route; mutation CSRF remains required. The picker is advisory: Sales/Purchase posting services still revalidate status, remaining quantity and idempotency in their existing transactions. See [returns-management.md](returns-management.md).

Sales invoice/list/post responses expose nullable `treasuryAccountId`, `treasuryAccountName` and `treasuryMovementId`. Cash posting automatically deposits in the shift-revenue cashbox in the same transaction; POS permission suffices without manual treasury access. See [sales-shift-revenue.md](sales-shift-revenue.md).

`/api/expenses/categories` supports GET/POST for saved types; `/api/expenses/vouchers` supports GET/POST for immutable idempotent expense documents with selected treasury withdrawals. Session/screen checks protect reads and writes; CSRF protects mutations. Full contracts: [expenses.md](expenses.md).

Unauthenticated first-run routes are limited to `GET /api/auth/bootstrap-status` and `POST /api/auth/bootstrap`. Status returns `{ required: true|false }`. Bootstrap accepts only `{ username, password, confirmPassword }`; the server fixes the role to `administrator`, requires a nonblank password with matching confirmation, atomically requires an empty `Users` table, and returns the normal session cookie on success. Any existing active or inactive user makes the POST return `409 bootstrap_unavailable`.

New monetary request fields accept invariant decimal text with at most two fractional digits. Quantity fields keep their existing scale-6 contract. Catalog price DTOs and formatted purchasing/inventory financial fields use two display digits; scaled integer fields remain scale 4 for exact auditing. Finalized invoice and supplier-account totals use nearest-piastre, midpoint-away-from-zero rounding.

Product configuration accepts `batch-tracking`, `expiry-dates`, `serial-numbers`, and `imei-tracking` in `capabilityKeys`. Application automatically includes batch when expiry is selected and serial when IMEI is selected. Catalog summaries include `hasBatchTracking` alongside the existing tracking flags. Physical intake endpoints are deferred; see [phase-2-task-3-tracking.md](phase-2-task-3-tracking.md).

## Operation log

GET /api/operation-logs?page=1&pageSize=50&search=...&from=yyyy-MM-dd&to=yyyy-MM-dd&userId=...&outcome=success|failure is administrator-only and returns paged authenticated API request/session audit entries with actor snapshot, UTC timestamp, method, path, status code and outcome. Search matches actor username/display name or path. The API audit handler excludes query strings and request bodies.

## Treasury and bank accounts

Customer statement GET and transaction POST now enforce `customer-statement` screen access for cashiers in addition to session/CSRF rules. `GET /api/customers/{id}/statement` includes unfiltered `currentBalance` and movement `notes`; `closingBalance` still represents the selected period. The existing transaction API supports both inline statement actions (`increase`, `collection`); historical idempotency rules are unchanged. Overflow returns 400 validation and logged database failures return 503 with retry identity preserved. See [customer-statement.md](customer-statement.md).

Installment Sales uses `GET /api/customers/search?query=...` for saved customer lookup and `GET /api/customers/{id}/statement` to show the selected customer's persisted balance and recent movements inline. The same statement endpoint backs the full account view; no duplicate account data is written by the installment screen.

`POST /api/suppliers/{id}/payments` now requires `treasuryAccountId` and effective `supplier-payment` permission plus the session/CSRF checks. It withdraws the amount from that account atomically with supplier settlement and invoice allocations; responses/history include `treasuryAccountId` and `treasuryMovementId`. Omitting invoice IDs automatically allocates by due date (invoice date fallback), then creation timestamp. Reads reflect allocated `paidAmount`/`remaining`. Missing source returns 400, insufficient funds/source conflict returns 409 with a `treasury_*` code, and logged database failures return 503 while preserving retry identity. Existing financial rows are not retroactively charged. See [supplier-payment-treasury.md](supplier-payment-treasury.md).

Supplier Accounts extends the existing `POST /api/suppliers/{id}/invoices` with optional `operationKey` (required by the new UI). Identical actor-bound requests replay the original invoice; changed supplier/payload/actor or a key owned by another financial operation returns `409 operation_conflict`. Invoice creation, the linked immutable supplier ledger entry and payable/credit projection are atomic. `GET /api/suppliers/{id}/invoices` additionally returns `documentStatus`, `returnedAmount` and return-adjusted nonnegative `remaining`. Purchase drafts cannot receive payments; payment DTOs select either `invoiceId` or `purchaseInvoiceId`. New debt invoice and payment inputs may use exact decimal text. See [supplier-accounts.md](supplier-accounts.md).

Cash purchase drafts now require `treasuryAccountId`; credit drafts require it to be null. Invoice reads include `treasuryAccountId`, `treasuryAccountName`, and nullable `treasuryMovementId`. `POST /api/purchases/{id}/post` atomically withdraws the full total from that account with stock receipt/FIFO, supplier settlement and audit. Missing account/funds return a `treasury_*` conflict and leave the draft/funds/stock unchanged. Purchase Management screen access permits account lookup and purchase-bound payment without granting manual treasury mutation permissions. Historical posted invoices are not retroactively charged. See [purchase-treasury.md](purchase-treasury.md).

All `/api/treasury/*` endpoints require the session cookie and return `{ success, data, error }`; mutations require `X-CSRF-Token`. Reading cash/bank accounts accepts any effective `accounts-list`, `account-deposit` or `account-withdraw` grant. The installment receivable summary accepts `accounts-list`, `installment-system`, or `installment-payment`. Account management requires `accounts-list`; deposit and withdrawal each require their own screen grant. Administrators retain full access.

- `GET /api/treasury/accounts`: all nondeleted cash/bank accounts with `id`, `code`, `name`, `type` (`cash`/`bank`), `notes`, `version`, exact `balance` text and internal `balanceScaled`. The frontend displays the exact string.
- `GET /api/treasury/installment-receivable`: noncash aggregate installment debt with exact `debitTotal`, `creditTotal`, and `balance` strings plus internal scale-4 values. The debit total is contract value including interest; credits include down payments, collections, and return debt reductions. This ledger is not a cash or bank account.
- `POST /api/treasury/accounts`: `{ code, name, type, notes? }`; returns `201` with the zero-balance account.
- `PUT /api/treasury/accounts/{id}`: those fields plus current `version`; returns the saved account. This cannot edit money.
- `DELETE /api/treasury/accounts/{id}?version=N`: deletes only unused accounts, retaining the tombstone/audit; returns `{ deleted: true }`.
- `POST /api/treasury/deposit` and `POST /api/treasury/withdraw`: `{ accountId, amount, notes?, operationKey }`, with positive invariant amount text and at most two decimals. Returns `201` with `id`, `accountId`, `type`, exact `amount`/`balanceAfter` text, underlying scale-4 fields, UTC `createdUtc`, `notes`, and `replayed`. A replay returns the original historical post-balance; read accounts for current balances. Request hashes are internal.

Errors include `400 validation`, `404 not_found`, `409 duplicate_code`, `version_conflict`, `account_in_use`, `insufficient_balance`, `balance_overflow`, and `operation_conflict`, plus authentication/CSRF/screen denial. Database errors are logged and return Arabic `503 database_unavailable`; the client retains retry identity. See [treasury.md](treasury.md) for atomicity and integration boundaries.

## Product catalog

Inventory movement report rows for sales use `route: "pos"` and `documentId` of the latest posted revision in the correction chain. The reference remains the original invoice number. Opening a row performs a read of `GET /api/sales/{id}`; it does not mutate financial or inventory records. Return and cancellation links continue to use sales management.

All catalog endpoints return the existing `{ success, data, error }` envelope, require an authenticated cookie, use effective screen access for cashiers, and require `X-CSRF-Token` on mutations. `salePrice` is required; `purchasePrice` is nullable and represents a reference/default acquisition cost, not inventory average cost. Both non-null monetary inputs are non-negative invariant decimal strings with at most two fractional digits and are stored in the scale-4 integer representation; they are never JSON binary-floating numbers. Product detail responses return `purchasePrice: null` when the cost is unknown.

- `GET /api/catalog/products`: bounded `page`/`pageSize` (maximum 100), `search`, exact `categoryId`, nullable `isActive`, and optional `includeArchived`. Each item also returns ordered `sizeValues` and `colorValues`, active `variantCount`, and persisted `hasExpiryTracking`, `hasSerialTracking`, and `hasImeiTracking` flags. Global feature disablement does not erase these saved summaries.
- `GET /api/catalog/products/{id}`; `POST /api/catalog/products`; `PUT /api/catalog/products/{id}`.
- `PUT /api/catalog/products/{id}/state`; `POST /api/catalog/products/{id}/archive` (administrator only).
- `GET|POST /api/catalog/categories`; `PUT /api/catalog/categories/{id}`. Writes are administrator-only.
- `GET|POST /api/catalog/units`; `PUT /api/catalog/units/{id}`. Writes are administrator-only.
- `GET /api/catalog/migration-issues` (administrator only).
- `GET /api/catalog/products/{id}` returns the product detail aggregate, including effective capability state, attribute values, product units/conversions, variants, SKUs, and barcode history.
- `GET /api/catalog/attributes?kind=all|custom&includeInactive=false` returns custom attributes and values only. Retired built-in attributes are unavailable for reads or writes. Administrator-only CSRF-protected writes are `POST /api/catalog/attributes`, `PUT /api/catalog/attributes/{id}`, `POST /api/catalog/attributes/{id}/values`, and `PUT /api/catalog/attribute-values/{id}`. Product lists omit `sizeValues`/`colorValues`; value contracts omit `colorHex`, and aggregate attribute commands accept value IDs rather than free-text `values`. Legacy variant identities remain usable through an opaque preservation path; see [retired product attributes](retired-product-attributes.md).
- `GET /api/catalog/barcodes/lookup?code=...` performs authenticated scanner lookup and returns the product, variant, unit, rational conversion, effective prices, and a non-sellable reason when archived/inactive/retired. It requires the effective `barcode-scanning` capability.
- EAN-13 scale labels are decoded after fixed product barcodes are checked. Each installation supports one scale profile, managed by an administrator through `GET /api/catalog/scale-barcode-profiles` and `POST /api/catalog/scale-barcode-profiles` (the list response contains zero or one profile). The profile maps a prefix, PLU length, weight-or-price value length/precision, optional value check digit, and active/version state. The 13th digit is validated as the EAN check digit; PLU is matched against an active product SKU. Weight values become kg quantities, while price values are converted using the product's effective price per kg.
- `POST /api/labels/barcodes/delete` retires exactly one saved barcode association using its product version and operation key; it does not delete product, inventory, or historical records. `POST /api/labels/product-preview` renders the selected saved barcode through the configured native label renderer and never creates a print job. A separate `POST /api/labels/jobs` request is required to submit printing.

Product create/update accepts `allowSaleWhenOutOfStock` to control whether a sale may be posted when available stock is below the requested quantity, plus an optional `configuration` object containing capability keys, attribute value assignments, product units (`numerator`/`denominator`), variants, per-variant SKUs, and multiple barcodes. Writes are atomic and administrator-only when configuration is supplied. Existing default variants remain compatible with simple Task 2.1 products.

Create product requires an `operationKey`. Reusing it with the same canonical request returns the first product; reusing it for different data returns HTTP 409 `operation_key_conflict`. Updates require `version`; stale writes return HTTP 409 `version_conflict`. Other stable codes include `invalid_category`, `invalid_unit`, `duplicate_category`, `duplicate_unit`, `category_cycle`, `review_required`, `archived`, `screen_forbidden`, and `invalid_csrf`.

## General settings endpoints

- `GET /api/settings/company`: authenticated company profile read.
- `PUT /api/settings/company`: administrator + CSRF protected company profile update.
- `GET /api/settings/general`: authenticated effective language/date/time/currency/tax settings.
- `PUT /api/settings/general`: administrator + CSRF protected validated update.
- `GET /api/settings/database-info`: administrator-only local path, size, migration count/latest name, journal mode, and foreign-key state. It cannot modify files.

All responses use the standard `{ success, data, error }` envelope. The only supported `languageCode` is `ar`, and `decimalPrecision` must be `2`; financial display is fixed to two digits while quantity formatting remains independent. Invalid formats, currency codes, precision, tax rates, email addresses, and inconsistent tax flags return `400 validation`. Database information returns no connection string or credentials.

All endpoints return `{ "success": true, "data": ... }` or `{ "success": false, "error": { "code": "...", "message": "..." } }`. Login, current-user restoration, and logout use the HttpOnly SameSite `alkhayal_session` cookie. JSON properties use camelCase.

- `GET /api/system/health` returns `{ status, utc, version }`.
- `POST /api/auth/login` accepts `{ username, password }`; success returns `{ id, username, displayName, role, csrfToken }` and sets the session cookie. Unknown users and invalid passwords return the same HTTP 401 credential error. A valid password for a disabled account returns the disabled-account response.
- `GET /api/auth/me` returns the same safe profile and current CSRF token for a valid, non-expired server-side session. Invalid or expired sessions return HTTP 401; expired records are deleted.
- `GET /api/auth/me/screen-access` returns `{ role, screenIds, generatedUtc }` after combining authentication, role, explicit cashier grants, administrator-only registry metadata, and effective feature state.
- `POST /api/auth/logout` requires the session cookie plus `X-CSRF-Token`. A missing or invalid token is rejected; success invalidates the session and expires the cookie.
- `GET /api/business-activities` requires an authenticated session and returns the active registry ordered by default priority. Each item includes `key`, `arabicName`, `description`, `defaultPriority`, `isActive`, and `suggestedCapabilities`.
- `GET /api/business-activities/selected` requires an authenticated session and returns `{ isConfigured, primaryActivityKey, activityKeys }`.
- `GET /api/business-activities/recommendations` requires an authenticated session. With no query it evaluates the saved selection; `?activityKeys=clothing,footwear` previews an unsaved selection. It returns deduplicated recommendations, source activity keys, Arabic reasons, newly recommended keys, recommendations that no longer apply, and preserved administrator override keys.
- `PUT /api/business-activities/selected` requires an authenticated `administrator` session and `X-CSRF-Token`. The body is `{ activityKeys, primaryActivityKey, applyRecommendations }`. It rejects unknown/inactive keys and a primary key outside the selection. Saving replaces only selection metadata; it does not delete business data. Recommendations are applied only when explicitly requested and never overwrite `administrator` capability rows.
Feature endpoints require authentication:

- `GET /api/features` returns stable catalog metadata for all core/optional modules and product capabilities.
- `GET /api/features/effective` returns resolved `modules`, `capabilities`, source/recommendation metadata, dependencies, and `generatedUtc`.
- `PUT /api/features/modules/{key}` and `PUT /api/features/capabilities/{key}` accept `{ isEnabled }`; administrator role and `X-CSRF-Token` are required. Unknown/core changes return 400 and dependency conflicts return 409.
- `POST /api/features/recommendations/preview` accepts `{ activityKeys }` and returns a read-only effective preview.
- `POST /api/features/recommendations/apply` accepts `{ activityKeys }`, requires administrator plus CSRF, applies dependency-complete recommendations, and preserves administrator overrides.

User-management endpoints require an authenticated administrator. Mutations additionally require `X-CSRF-Token`: `GET/POST /api/users`, `GET/PUT /api/users/{id}`, `PUT /api/users/{id}/status`, `POST /api/users/{id}/reset-password`, and `GET/PUT /api/users/{id}/screen-permissions`. They return 400 for validation/role/screen errors, 401 for missing sessions, 403 for cashier or CSRF failures, 404 for missing users, and 409 for duplicate usernames or last-active-administrator protection. Passwords and hashes are never returned.

Static frontend files, including `frontend/data/screens.json`, are served from the same OWIN origin with `Cache-Control: no-store, no-cache, must-revalidate`, `Pragma: no-cache`, and an expired response. This keeps the shell scripts and route registry on one deployment version in persistent WebView2 profiles.

Other business-screen operations do not yet have HTTP contracts: their UI state is explicitly in-memory and must not be interpreted as durable server behavior. Customer records and customer payments are exceptions: customer management endpoints persist customer data in SQLite.

Customer installment contracts are persisted by `POST /api/customers/{id}/installments` (screen permission `installment-system`, session and CSRF required); the request includes product ID and catalog price, down payment, interest percentage, count, interval months, first due date, and operation key. The API verifies the active catalog price. `GET /api/customers/{id}/installments` and `POST /api/customers/{id}/installments/{contractId}/payments/{number}` require `installment-payment`; payment also requires CSRF and includes paid date and operation key. Contract creation, customer-ledger debit/down-payment credit, schedule, installment payment, and statement ledger collection commit atomically. Identical retries return the saved contract; key reuse with different content conflicts. See [installments.md](installments.md).

- `GET /api/customers` returns the authenticated user's customer records from SQLite.
- `POST /api/customers` creates a customer; `PUT /api/customers/{id}` updates one; `DELETE /api/customers/{id}` deletes one. All writes require the session cookie and `X-CSRF-Token`. Customer codes are unique. The customer management list and add/edit/delete actions use these endpoints; other business screens remain session-only unless explicitly implemented.

Customer creation without a code allocates the next available `CUS-` numeric code in the database write transaction and returns it in the customer response. Existing codes are unchanged; explicitly supplied codes remain supported for existing API clients. Concurrent writers are serialized by SQLite and the unique code constraint.

`GET /api/suppliers?search=...&page=1&pageSize=25` returns `{items,totalCount,page,pageSize}`, ordered by name and ID. Search matches name, code, contact or phone. `GET /api/suppliers/{id}` returns one supplier for an existing purchase draft. The unpaged request remains available to dependent screens. `GET /api/inventory/balance-page?warehouseId=1&search=...&page=1&pageSize=25` returns a page of warehouse balance rows with FIFO completeness, searching product name, active SKU or active barcode. Each row represents a variant and batch; counts refer to balance rows. Both page sizes are bounded to 100.
- `POST /api/customers/{id}/transactions` (`type` of `increase`/`collection`/`reduction`, positive `amount` with at most two decimal places — larger precision is rejected with 400 `validation`, never silently rounded; the ledger stores it scaled to 4 decimal places, `occurredOn` as `yyyy-MM-dd`, optional `notes` of at most 1000 characters, required `operationKey` ≤120 chars) records an idempotent customer-ledger transaction and updates `Customers.Balance` in one SQLite transaction. An identical retry of the same operation key returns the first transaction again with `replayed: true`. Reusing the key with a changed amount/type/date/notes or as a different customer returns HTTP 409 `operation_key_conflict` (same convention as sales/purchasing/catalog/inventory) and changes nothing. Notes are compared exactly as submitted: `null` is normalized to the empty string on both sides, but leading/trailing whitespace is never trimmed, so a whitespace-only change is a different request. Collisions with rows written by other financial paths are also rejected, decided from stored ownership metadata only — no key prefix is reserved (a manually chosen operation key may start with `CP-` or `sale-` and still replays identically whenever it matches this posting path's own row): sales invoice/payment/return rows populate the `Reference`, `SalesInvoiceId`, or `SalesReturnId` columns and carry a `RequestHash` that differs from the `OperationKey`; customer-payment rows are identified by an existing `CustomerPayments` row whose `Reference` equals the `OperationKey`, queried in the same transaction (the flow's ledger row keeps its original insert, which does not populate `Reference`); unrelated `opening`/`legacy_payment` ledger rows were never written by this posting path. Validation errors return 400 (`validation`); missing customers return 404 (`not_found`).
- Suppliers are also persisted. All endpoints require the session cookie; writes also require `X-CSRF-Token`. Legacy supplier invoices/payments remain stored in their original tables. New integrated purchasing and supplier-ledger monetary inputs permit at most two fractional digits, persist exact scale-4 integers, and use `yyyy-MM-dd` dates.

## Sales invoices, collections, and returns (Phase 5)

- `GET /api/sales/{id}` returns the invoice and saved line snapshots.
- `POST /api/sales/drafts` creates a versioned draft; `PUT /api/sales/{id}` updates a draft only.
- `POST /api/sales/{id}/post` accepts `{ operationKey }` and atomically posts the invoice and a `manual_issue` inventory document through the shared FIFO transaction path.
- `POST /api/sales/{id}/payments` accepts `{ amount, method, treasuryAccountId, operationKey, occurredOn, notes? }` for an idempotent collection on a posted credit invoice. Methods are `cash`, `card`, or `transfer`.

### FR-002 customer collection destination

Every new receivable collection must supply a positive `treasuryAccountId` for an existing active account. `cash` requires a cash account; `card`, `transfer`, and `wallet` require a bank account. The same rule applies to `POST /api/customers/{id}/transactions` when `type=collection` (`method` and `treasuryAccountId`), to installment payments, and to the legacy `POST /api/customers/{id}/payments` (`operationKey` is now required). A positive installment down payment includes `treasuryAccountId` for a cash account; a positive cash maintenance delivery includes `treasuryAccountId`. A missing destination fails before posting; an inactive/missing/incompatible account produces a treasury conflict. No destination is inferred from ShiftRevenueTreasury. Old requests lacking these fields can still read historical data, but a new collection request cannot post without them. Historical collection rows are never backfilled. Each successful collection writes one customer ledger entry and one source-linked treasury deposit in a single SQLite transaction; cash also associates the active cashier shift when present. Shift close does not deposit again. Collections remain outside sales revenue reporting.
- `POST /api/sales/{id}/returns` accepts `{ operationKey, reason, lines: [{ invoiceLineId, quantity, serials? }] }`. Each line is capped at the unreturned quantity. The transaction restores stock and original FIFO layer lineage, writes the return, refunds cash already received, and applies any eligible remainder as a customer credit adjustment.

Draft lines contain `variantId`, `productUnitId`, `quantity` (up to six decimals), `unitPrice` and optional line `discount` (EGP, at most two decimals), plus `manualPriceOverride` for a cashier-edited rate. The invoice includes `customerId`, `warehouseId`, `invoiceDate`, `paymentMode` (`cash` or `credit`) and optional invoice `discount`. Credit requires a customer. The server confirms active product, variant, sale unit and current catalog price during draft save, applies persisted tax settings, and recalculates totals. For an automatically priced base-unit line at a quantity tier, `unitPrice` is the displayed piastre-rounded rate; the authoritative line total is calculated from the selected additional unit's price and exact conversion ratio, rounded once to piastres. Configured batch/expiry and serial/IMEI identifiers are checked against available stock at posting. Sales consume no more than available stock; uncovered quantity remains invoiced with incomplete cost coverage. Posting returns a conflict for unresolved FIFO cost, stale draft, or a reused operation key with conflicting data. Payment and return routes require session/CSRF protection and the corresponding cashier screen permission; administrators retain access. Customer statements include invoice and return references. Credit invoice creation and noncash return adjustments do not post a collection deposit; later customer payments do. Receipt/reprint is browser thermal print output and does not claim confirmation of printer hardware state.

Sale line responses include `productId` so invoice editing can reload the current unit configuration while retaining the saved invoice snapshot until a change is made.

# Stabilization Part 1: sales cancellation and inventory valuation

`POST /api/sales/{id}/delete-draft` accepts `{operationKey}` and hides an eligible draft from normal history. The draft and its audit remain in storage; no inventory or customer ledger entry is reversed. `POST /api/sales/{id}/cancel` accepts `{operationKey,reason}`. An eligible unpaid credit sale gains a `canceled` projection in the sales list/detail, an immutable cancellation record, a reversing stock document with FIFO cost layers, and a customer `reduction` ledger entry in one SQLite transaction. Both calls return the normal `{success,data,error}` envelope. An identical retry returns `data.replayed=true`; a changed request with the same key returns `operation_key_conflict` (409). Posted cash sales, invoices with payments or returns, tracked units, and ambiguous later customer collections return a specific 409 conflict; they remain unchanged.

`GET /api/inventory/valuation?warehouseId={id}[&productId={id}]` returns an on-demand aggregate: `costValue`, `potentialSellingValue`, and `estimatedGrossMargin` as invariant-culture decimal strings with four places, plus completeness flags and variant count. A null amount means the source data is incomplete or inconsistent; clients must not treat it as zero. Values are for remaining FIFO layers, current selling prices, and the selected warehouse. The margin is potential, not realized profit.

# Stabilization Part 2: Touch POS reads and discount input

`GET /api/inventory/products?posWarehouseId={id}&page={n}&pageSize={n}[&search=...][&categoryId={id}]` is the bounded Touch POS browse request. It requires sales-read access and an active warehouse. Barcode printer assignment: `PUT /api/labels/printer-assignment` (administrator, session and CSRF) accepts `{ version, printerName, paperName?, widthMm?, heightMm? }`. The active Windows paper is used when `paperName` is omitted. An explicit supported form or paired one-time width/height override can be saved. The response is the versioned `LabelSettings`. `GET /api/printing/printers` now reports `activePaper`, `dpiX`, `dpiY`, `landscape`, `printableWidthMm`, `printableHeightMm`, hard margins and a best-effort status alongside supported forms; these are driver reports, not physical media detection. `GET /api/labels/product-info/{barcodeId}?format=code128|ean13` returns the authoritative saved barcode and label fields for the compact Product Directory dialog. `POST /api/labels/jobs` accepts `exactQuantity: true` for Product Directory, which ignores profile batch copies while preserving application-level copy expansion for ordinary batches.

`PUT /api/labels/design` requires an administrator session and CSRF token. It accepts `{ version, elements }` and returns the updated `LabelSettings` with its saved `design`. Each ordered element supplies `key`, `visible`, `fontSize` (5–36 pt in quarter-point increments), `alignment`, and optional `bold` and `text`. A visible `barcode` is required for customization. Send `elements: null` to reset the design while retaining the printer and stock. `POST /api/labels/design/preview` accepts the same draft plus an optional `stockOverride` with `printerName`, `widthMm`, and `heightMm`, and returns `{ pngBase64 }` with sample data. Preview does not write settings or create a print job.

## Saved document preview

`POST /api/printing/preview/document` accepts `{ template, documentType, documentId }` from an authenticated administrator with a valid CSRF token. It validates the draft template, loads a posted document through `IPrintDocumentProvider`, and returns `{ success, data: { pngBase64, message }, error }`. Missing or inaccessible documents return `not_found`; it never submits a print job or changes the saved template. The preview uses the same native renderer as physical printing. The caller must label sample and actual previews distinctly.

`PUT /api/printing/settings` accepts the optional `profiles[].useDocumentTemplate` flag. When true, the profile's `templateId` selects its document-specific saved template even with a configured printer. When false or omitted, configured printers continue selecting their own template as before. The backend validates a document-specific template against the assigned printer before saving.

`GET /api/printing/documents?type={type}&q={text}` is administrator-only and returns at most 25 persisted, printable document choices `{ id, reference, party, date, amount }`. It searches saved sales, delivery invoices, purchases, returns, customer/supplier payments, and shifts. The choice is only a picker projection; actual preview and print reload the authoritative document by type and ID. `q` may be empty to show recent records.

## Expiry-only inventory contract

Stock-entry requests for an expiry-tracked product send `expirationDate` and quantity; `lotNumber` is optional internal compatibility data and is not requested from operators. Positive expiry-tracked entries require `expirationDate`. Sale requests omit lot and expiry selection; the server allocates stock in original FIFO order. Linked sales-return lines may send `isDamaged` (default `false`). The server restores quantities from the sale's actual stock allocations, latest expiry first, and retains expired or damaged returns outside sellable stock. Legacy invoice allocations remain readable through the existing return contract.

### Suspended sales invoice count
`GET /api/sales/suspended-count` returns `{ success: true, data: { count: number }, error: null }` for authenticated users allowed to view sales. The count includes persisted, visible sales drafts only; deleted drafts, posted invoices, cancellations, and superseded correction records are excluded. Internal draft status and write contracts remain unchanged.
# Inventory movement source display

The existing paged `GET /api/inventory/movements` response now includes nullable `sourceInvoiceType` (`purchase` or `sale`), `sourceInvoiceId`, and `sourceInvoiceNumber` on each movement. The store resolves these from saved invoice records in the page query. `notes`, document IDs, filters, paging, and reversal semantics remain unchanged. Clients should show the saved invoice number only when resolved; a missing source record must be described without inventing a number.

### Invoice history pages

`GET /api/sales/page` accepts `search`, a one-based `page` (default 1), and `pageSize` (25, 50, 100, or 200, default 50). It returns `items`, `totalCount`, `page`, and `pageSize`. Search matches the visible invoice number or customer name across all visible invoices. Results are ordered by descending invoice ID.

`GET /api/purchases/page` accepts a one-based `page` (default 1) and returns `items`, `totalCount`, and `page` with a fixed size of 50. Results are ordered by descending invoice date and ID. Both routes clamp a page beyond the end to the final page and report page 1 for empty results. Existing collection, detail, and export routes retain their contracts.

`GET /api/returns/page` accepts `search`, a one-based `page`, and `pageSize` of 25, 50, 100, or 200 (default 50). It returns `items`, `totalCount`, `page`, and `pageSize`. Search covers return number, original invoice number, and party. History order is descending creation time, return type, then descending ID.

`GET /api/expenses/vouchers/page` accepts a one-based `page` and returns a fixed 50-row page with `items`, `totalCount`, and `page`, ordered by descending voucher ID. Both endpoints adjust out-of-range requests to the last page and retain their existing permissions and compatibility routes.

`GET /api/customers/page` requires customer-directory access. It accepts `search`, a one-based `page`, `pageSize` of 25, 50, 100 or 200, `sort` and `descending`. The default is 50 customers in ascending code order. It returns `items`, `page`, `pageSize` and `totalCount`.

`GET /api/customers/{id}/statement` accepts optional `page` and `pageSize`. When paging is requested, period totals and balances cover the full matching ledger, and running balances include movements before the current page. The synthetic opening row appears only on page 1 and is excluded from `totalCount`. Existing callers that omit `page` keep the full statement behavior.

`GET /api/workforce/advances/history` accepts optional `employeeId` and one-based `page`. `GET /api/workforce/payroll/history` accepts `employeeId`, `period` and one-based `page`. Both use fixed 50-row history pages and existing workforce access checks. Payroll additionally returns `pendingAdvance` and `alreadyPaid` for the selected employee and period, calculated independently of the history page.
